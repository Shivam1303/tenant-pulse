User guide

Tenant Pulse

A local load tester for multi-tenant APIs. It runs a collection of HTTP requests for many tenants at once, each with its own login token and variables, then reports latency percentiles, errors and a PASS or FAIL verdict.

Runs on your machine only Up to 1,000 virtual users Runs up to 10 minutes Node.js 24 · Next.js

01Overview

What it does, and what happens when you press Start run.

Requests

Build the API calls to test, like a small Postman: method, path, params, headers, body.

Tenants

The clients to test as. Each has its own login or token and its own values such as orderId.

Run

Choose how many virtual users per tenant, for how long, and the limits a run must stay under to pass.

Results

Live charts while it runs, saved reports afterwards, and trends across runs.

What happens during a run

Preflight is a safety net: if a login fails or a request returns an error for any tenant, no load is sent and you see exactly which tenant and request failed.

02Install & start

About five minutes on a fresh machine.

You need

  • Node.js 24 (20.9 or later also works). The easiest route is nvm; the repo has an .nvmrc.
  • Git, and network access to the API you want to test.
  • Optional: the mysql command-line client, only if you want the MySQL connection panel.
  1. Get the code 
    $ git clone git@github.com:Shivam1303/tenant-pulse.git
$ cd tenant-pulse
  2. Start it

    The script switches to Node 24, installs the web dependencies the first time, and starts both the API service and the web app.

    $ ./run.sh          # development mode, hot reload
$ ./run.sh prod     # optimised build, then start
  3. Open the app

    Go to http://127.0.0.1:3000. Press Ctrl+C in the terminal to stop both processes.

Prefer to run the steps yourself? 
$ nvm use
$ npm --prefix web install
$ npm run build
$ npm start        # or: npm run dev
Using different ports

The web app uses port 3000 and the API service 4174. Change them with environment variables:

$ WEB_PORT=3200 API_PORT=4300 ./run.sh prod

For a production build, API_PORT must be set when building as well as when starting, because the web app's proxy target is fixed at build time.

Local only

Both processes listen on 127.0.0.1 and reject requests from other hosts, so the app is not reachable from the network. Everyone who uses it runs their own copy.

03Key ideas

Five terms that explain everything else in the app.

TermMeaning
PlanWhat to test and how hard: requests, login request, load settings and pass criteria. Pick or create plans from the menu at the top.
EnvironmentWhere to test, such as Local or Staging: a base URL, shared variables and that system's tenants with their credentials. Pick it next to the plan at the top. Several plans can use one environment.
TenantOne client of your API, in one environment. It has a client number, and either a username and password (the app logs in for it) or a pasted bearer token, plus its own variables.
Virtual user (VU)A simulated person. Each VU calls a request, pauses, then calls the next one, looping through all enabled requests in order. Total VUs = tenants × VUs per tenant, capped at 1,000.
Think timeThe pause after each call, like a user reading the screen. It varies by ±50% so users drift apart. With 0 think time, every VU sends requests as fast as the API answers.
p50 / p95 / p99Latency percentiles. p95 = 250 ms means 95% of calls finished within 250 ms. p95 is the usual number to watch.

Variables

Write {{name}} anywhere in a path, query value, header or body, and each tenant fills in its own value. These are always available:

VariableValue
{{token}}The tenant's bearer token, from the login request or pasted in.
{{client}}The tenant's client number.
{{username}}The tenant's username.
{{baseUrl}}The environment's base URL.
{{password}}Only inside the login request.

Anything else, such as {{orderId}}, is a tenant variable. When a request uses it, a matching field appears on every tenant automatically. A value that is the same for all tenants of an environment can be set once as a shared variable on the Environments screen; a tenant's own value wins. Values are escaped for JSON bodies and URL-encoded in paths, so you never need to quote them yourself.

04Your first run

From an empty plan to a report.

  1. Set the environment

    Pick the environment at the top (or create one on Environments) and enter its base URL, for example https://api.staging.example.com. The base URL is also editable at the top of the Requests collection.

  2. Add and try a request

    Add a request (e.g. GET /products), or import one from a cURL command or a Postman collection. Pick a tenant in the response panel and click Send. It calls the API once with your unsaved edits so you can check the response before running load.

  3. Add tenants

    On Tenants, add each client of the current environment with its login or token and fill in any variables. Each row shows whether that tenant is ready. Many tenants? Use Import CSV.

  4. Check the login request

    On the Login request tab, confirm the endpoint and where the token sits in the response (e.g. token or data.accessToken). Then open a tenant and click Test login (or Check token for token tenants).

  5. Choose the load

    On Run, start small: 2 VUs per tenant, 30 s ramp-up, 2 minutes total, 1000 ms think time. Set pass criteria, e.g. p95 under 500 ms and errors under 1%.

  6. Check, then start

    Click Check only to run just the preflight. When it passes, click Start run and watch Results → Live.

Write requests change data

POST, PUT, PATCH and DELETE requests need an explicit confirmation before Send, preflight or a run, because they can create or delete real records. Point them at a test environment.

05Screen by screen

The five screens in the left sidebar.

Requests

/workspace/requests
  • Three panes: the collection, the request editor and the response.
  • The switch next to each request includes it in or leaves it out of the run.
  • Editor tabs: Params, Headers, Body (JSON, text or form) and Auth. Tenant bearer token sends Authorization: Bearer {{token}}.
  • A path can be relative (/orders), a full URL (https://other-host/orders), or start with a variable ({{apiHost}}/orders) so each tenant can hit its own server.
  • Import (the arrow next to +): paste a cURL command (Copy as cURL in the browser or Postman) or choose a Postman collection v2.1 file. A preview shows each request and anything that couldn't be carried over. Bearer auth becomes the tenant token, URLs on the environment's base URL become paths, and collection variables can go into the environment.

Tenants

/workspace/tenants
  • Tenants tab: the clients of the current environment, with a ready indicator and an on/off switch. Switched-off tenants stay in the environment but are skipped, in every plan that uses it.
  • Each tenant uses Login (username + password) or Bearer token (pasted).
  • Import CSV takes columns client,username,password,token; every other column becomes a variable.
  • Login request tab: the call made once per login tenant during preflight, and the response path of the token. Tokens are not refreshed during a run.
client,username,password,token,orderId,departmentId
1001,loadtest,secret,,58213,4
1002,,,eyJhbGciOi...,77120,2

Environments

/workspace/environments
  • One entry per system you test: name, base URL, shared variables and its tenants, plus the plans that use it.
  • Duplicate with tenants copies an environment with its saved credentials, a quick start for a new system. Import Postman creates one from a Postman environment export.
  • An environment used by a plan can't be deleted. Switch the plan first.

Run

/workspace/run
  • Target: environment, plan name and a run label (e.g. release-2.4) shown on saved reports.
  • Tenants: tick which ones take part.
  • Load profile: total duration (up to 10 minutes, ramp-up included), VUs per tenant, ramp-up, think time and timeout. The chart and the peak VU count update as you type, and the screen shows the highest request rate the setup can produce.
  • Pass criteria: a p95 limit and an error-rate limit decide the verdict.
  • Start run saves, runs preflight, then starts the load. Check only runs just the preflight.

Results

/workspace/results
  • Live: per-second throughput, p50/p95/p99 latency, error rate and active VUs, a failure breakdown, and sortable tables by request and by tenant.
  • Reports: every saved run with its verdict. Open one, export JSON or CSV, or tick two to compare them side by side.
  • Trends: all runs of the current plan, oldest to newest, for p95, p50, p99, error rate or requests/sec, overall or per request. The pass limit shows as a dashed line; filter by environment (it starts on the current one) and by run label.
  • While a run is active, a bar at the top of every screen shows progress, rate, p95, errors and a Stop button.

Unsaved edits are marked in the top bar. Save with Ctrl/⌘+S. Switching plans or closing the tab with unsaved edits asks first.

06Reading results

How to tell whether the API held up, and whether to trust the numbers.

PASS

p95 stayed under the limit and the error rate stayed under its limit for the whole run.

FAIL

At least one limit was exceeded. The report says which one.

What counts as an error

Any non-2xx status, timeout or network error. With the success-field check on, a 2xx body with "success": false also counts.

Things to watch

  • Rising p95 while VUs ramp up usually means the API or database is reaching its limit.
  • Errors concentrated on one tenant (tenant table) point to data or permissions for that client, not general load.
  • Many 401s mean a token expired or was rejected. Tokens are not refreshed mid-run.
When the tester itself is the bottleneck

All VUs run in one Node process. At high VU counts or with 0 think time, your own machine can fall behind. The live view warns about this (event-loop lag). When it does, the latencies include the tool's own delay, so reduce VUs or add think time.

MySQL panel (optional)

Add a MySQL host to sample Threads_connected and Threads_running once per second during the run, using the installed mysql client. The user only needs permission to read global status. Without a host, the panel shows Not measured.

07Command line

Run a plan built in the UI from a terminal or CI job, with the same report format.

$ node service/cli.js --plan default --preflight-only   # just the checks
$ node service/cli.js --plan default                   # full run
$ node service/cli.js --plan default --allow-writes    # plan has POST/PUT/PATCH/DELETE
$ node service/cli.js --plan default --env staging     # another environment than the plan's

The CLI exits with code 1 when preflight fails or the verdict is FAIL (without pass criteria: when any call failed), so it can gate a pipeline. Ctrl+C stops new requests and waits for calls in flight.

Tests

$ npm test

Runs the engine and API routes against a built-in mock API, using a temporary data folder. Your saved plans are not touched.

08Data & secrets

Where things are stored, and what never leaves your machine.

File in service/data/Contents
plans.jsonAll plans, without passwords or tokens.
environments.jsonEnvironments: base URLs, shared variables and tenants, without passwords or tokens.
secrets.jsonPasswords and tokens, written with owner-only file permissions.
report-<id>.jsonOne file per finished run.
reports-index.jsonSummaries used by Reports and Trends. Rebuilt automatically if missing.
Secrets stay local

The browser never receives saved passwords or tokens; it only sees that one is set. Leaving a password field blank keeps the saved value. Reports and exports exclude passwords, tokens and authorization headers. The data folder is ignored by Git.

To move plans to another machine, copy service/data/. To start fresh, stop the app and delete that folder.

09Troubleshooting

Common problems and fixes.

nvm not found when running ./run.sh

Install nvm, or set NVM_DIR to where it is installed. Alternatively, use Node 24 another way and run npm run dev.

Syntax errors or odd failures on start

You are probably on an old Node. Check with node -v; it must be 20.9 or later (24 recommended). Run nvm use in the project folder.

Port 3000 or 4174 already in use

Another copy is running, or another app has the port. Stop it, or start with other ports: WEB_PORT=3200 API_PORT=4300 ./run.sh.

Preflight fails for a tenant

The failure list names the tenant, the request and the status. Try that tenant with Send on Requests, or Test login on that tenant. Common causes: wrong password, a token path that doesn't match the response, or a missing variable.

“A check or run is already active.”

Only one preflight or run can happen at a time. Wait for it to finish or click Stop in the run bar.

Many 401 errors partway through a run

Tokens are fetched once in preflight and not refreshed. If they expire during the run, calls fail with 401. Use a shorter run or longer-lived tokens.

Web app shows errors after changing API_PORT in production

The production build fixes the API port when it is built. Rebuild with the new port: API_PORT=4300 ./run.sh prod.
